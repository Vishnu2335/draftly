Section 01

Project Overview

Product definition, mission statement, non-Google Docs identity, and core value propositions.

Draftly is a modern full-stack document workspace where professionals, engineers, and creators create, organize, edit, import, and share substantive documents.

⚠️
Mandatory Design Identity: Anti-Google Docs Mandate

Draftly must possess its own unique product identity. Under no circumstances should Draftly copy Google Docs, its simulated 8.5" × 11" white sheet margins, its multi-tiered cluttered top toolbars, or its corporate blue-and-white visual language. Draftly is conceived as a modern, calm productivity and writing workspace—tactile, spacious, responsive, and distraction-free.

File Ingestion Mangles external file formatting and forces conversion into proprietary Google Drive format. High-fidelity AST extraction for DOCX, MD, and TXT with instant editable rehydration.
Workspace Feel Sterile corporate office suite, high cognitive load, heavy background telemetry. Calm, tactile atelier using Forest Green, Warm Stone, Ivory, and Sage tones.

Section 02

Problem Statement

Key frictions and breakdowns in current document creation and sharing tools.

Knowledge workers spend hundreds of hours every year writing inside tools that hinder rather than amplify their thinking. Existing platforms suffer from four foundational problems:

1. Interface Bloat & Cognitive Fatigue

Legacy processors present users with dense toolbars, margins, and printing rulers left over from the desktop publishing era. Over 80% of buttons are never clicked, yet they clutter the screen and create constant distraction.

2. Markdown vs. Rich Text Divide

Technical creators love markdown shortcuts and structural clarity, but non-technical collaborators need visual formatting. Modern teams are forced to choose between raw syntax and clunky WYSIWYG editors.

3. Broken File Import Workflows

Importing a Microsoft Word (.docx) or Markdown document into existing web suites regularly destroys heading hierarchies, code indentations, and list structures, requiring tedious manual reformatting.

4. Permission Confusion & Accidental Leaks

Unclear sharing interfaces make it difficult to determine who has edit versus view access, leading to accidental document overwrites, permission escalation, or sensitive drafts being visible to unintended viewers.

Section 03

Goals and Objectives

Core engineering targets, user experience benchmarks, and measurable KPIs.

  • Sub-50ms Keystroke Latency: Maintain instantaneous typing response without stutter or DOM delays even on long-form documents.
  • Universal 1-Click Import: Seamlessly ingest Word (.docx), Markdown (.md), and plain text (.txt) files up to 10MB in under 2 seconds.
  • 100% Autosave Reliability: Guarantee that zero user edits are lost through a debounced autosave pipeline paired with explicit manual save commands.
  • Strict Role-Based Sharing: Implement clear Owner, Editor, and Viewer permission boundaries backed by segregated dashboard repository tabs.
  • Zero-Friction Onboarding: Enable a new user to register, view the dashboard, and draft or import their first document in under 10 seconds.

Section 07

Authentication and User Management

Registration, login, password security, JWT session management, and route guarding.

Feature Endpoint Technical Specification & Acceptance Criteria
User Registration POST /auth/register Accepts name, email, and password. Validates standard email syntax and minimum 8-character password. Hashes password using bcrypt (cost factor 12). Returns 201 Created with user profile (omitting password hash).
User Login POST /auth/login Verifies email and password hash. Issues a signed JSON Web Token (JWT) with HS256 algorithm and 24-hour expiration. Returns JWT access token and user identity object.
Current User Profile GET /auth/me Authenticated endpoint. Decodes caller's JWT token and returns user profile details (id, name, email, created_at).
Route Guarding Next.js Middleware Edge middleware intercepts navigation to /dashboard and /document/*. Unauthenticated requests are redirected immediately to /login.

9.2 Save Pipeline & Status Indicators

Autosave Engine (1000ms Debounce)

The editor monitors typing mutations and triggers an asynchronous debounced payload to PUT /documents/{id} exactly 1000ms after the user pauses typing. Manual save is available via Ctrl+S or the Save button.

Live 4-State Status Pill
  • ● Saved: All changes persisted to Supabase PostgreSQL.
  • ○ Saving...: Network write request in flight.
  • △ Unsaved changes: Mutation occurred; debounce timer active.
  • ✕ Error syncing: Network failure; retry action enabled.
Section 10

File Upload and Import (TXT, MD, DOCX – 10 MB)

Multi-format ingestion pipeline, AST extraction via python-docx, validation rules, and error handling.

Format Parser Tooling Extraction Strategy Output Structure
.docx python-docx Parses Word document paragraphs, headings (Title, H1, H2), bullet lists, and inline formatting runs (bold, italic, underline). Structured semantic HTML matching Tiptap schema.
.md UTF-8 Stream Reader Parses Markdown headers (#, ##), lists (-, 1.), bold (**), and italic (*). Structured semantic HTML matching Tiptap schema.
.txt UTF-8 Stream Reader Reads plain text lines, sanitizes special characters, and preserves paragraph breaks. Semantic paragraphs (<p>).
📁
Upload Validation & Ingestion Workflow

• Maximum File Size: Strictly enforced at 10 MB (10,485,760 bytes) on both the client dropzone and FastAPI backend. Files exceeding 10 MB return 413 Payload Too Large.
• Instant Document Generation: Upon successful extraction via POST /documents/import, the backend creates a new document owned by the uploader titled after the original filename (e.g. Roadmap_2027.docx becomes "Roadmap 2027") and redirects the user directly into the active editor.
• Error Handling: Corrupted archives, password-protected Word docs, or unsupported binary extensions trigger actionable user notifications without crashing the session.

11.2 Sharing Modal & Backend Enforcement

  • Share Dialog: Document owners can open the Share Modal, input a collaborator's email address, and select a role (editor or viewer).
  • Collaborator List & Revocation: Displays all active collaborators with their roles. The owner can click "Revoke Access" to immediately remove access via DELETE /documents/{id}/shares/{user_id}.
  • Backend Permission Guarding: FastAPI authorization dependencies verify user role against document_shares and documents.owner_id before allowing any mutating operation. Unauthorized requests return 403 Forbidden.
  • Read-Only Canvas: For Viewers, Tiptap is initialized with editable: false, the formatting toolbar is hidden, and a "View Only" badge is displayed.
Section 12

Database Schema

Relational entity models in Supabase PostgreSQL: Users, Documents, Document_Shares, and Attachments.

Draftly uses Supabase PostgreSQL as its dedicated relational database provider. The schema enforces strict foreign key constraints, cascading deletions, and performance indexes.

1. Table: users

Column Type Constraints Description
id UUID PRIMARY KEY, DEFAULT gen_random_uuid() Unique identifier for the user account.
name VARCHAR(255) NOT NULL Full display name of the user.
email VARCHAR(320) NOT NULL, UNIQUE Unique normalized lowercase email address.
password_hash VARCHAR(255) NOT NULL One-way salted password hash generated via bcrypt.
created_at TIMESTAMPTZ NOT NULL, DEFAULT NOW() Account creation timestamp.

2. Table: documents

Column Type Constraints Description
id UUID PRIMARY KEY, DEFAULT gen_random_uuid() Unique identifier for the document.
title VARCHAR(500) NOT NULL, DEFAULT 'Untitled Document' Display title of the document.
content JSONB / TEXT NOT NULL, DEFAULT '{"type":"doc","content":[]}' Structured Tiptap ProseMirror AST (or semantic HTML string).
owner_id UUID NOT NULL, REFERENCES users(id) ON DELETE CASCADE Foreign key linking to document creator.
created_at TIMESTAMPTZ NOT NULL, DEFAULT NOW() Document creation timestamp.
updated_at TIMESTAMPTZ NOT NULL, DEFAULT NOW() Timestamp of latest save. Indexed for sort performance.

3. Table: document_shares

Column Type Constraints Description
id UUID PRIMARY KEY, DEFAULT gen_random_uuid() Unique identifier for the share permission.
document_id UUID NOT NULL, REFERENCES documents(id) ON DELETE CASCADE Foreign key linking to shared document.
shared_with_user_id UUID NOT NULL, REFERENCES users(id) ON DELETE CASCADE Foreign key linking to collaborator user.
permission VARCHAR(20) NOT NULL, CHECK (permission IN ('editor', 'viewer')) Assigned role: editor (read/write) or viewer (read-only).
created_at TIMESTAMPTZ NOT NULL, DEFAULT NOW() Timestamp when share was created.

Unique Constraint: UNIQUE(document_id, shared_with_user_id) prevents duplicate permission rows.

4. Table: attachments

Column Type Constraints Description
id UUID PRIMARY KEY, DEFAULT gen_random_uuid() Unique identifier for attachment.
document_id UUID NOT NULL, REFERENCES documents(id) ON DELETE CASCADE Foreign key linking attachment to parent document.
filename VARCHAR(500) NOT NULL Original name of uploaded file (e.g. Specifications.docx).
file_type VARCHAR(100) NOT NULL MIME type of file.
file_size INTEGER NOT NULL, CHECK (file_size <= 10485760) Size in bytes (maximum 10MB limit enforced).
storage_path VARCHAR(1000) NOT NULL URI pointer to file in persistent object storage (production) or local disk (dev).
💡
Storage Rationale: Database Metadata vs. Object Storage

All relational structures, document ASTs, permission mappings, and file metadata reside in Supabase PostgreSQL for ACID transactions and sub-millisecond query performance. Uploaded raw binary files (DOCX, MD) are streamed directly into persistent object storage (e.g. Supabase Storage / S3) rather than storing heavy byte blobs in PostgreSQL tables.
